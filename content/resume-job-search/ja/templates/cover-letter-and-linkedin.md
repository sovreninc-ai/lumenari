# カバーレター + LinkedIn リライト

> 声を共有する 2 つの成果物。カバーレターは約 30% の確率で読まれる — それでも書く、そして短く。LinkedIn はカバーレターより頻繁に読まれ、人々が思っている以上に重要。

---

## パート 1 — カバーレター

### プロンプト

```
ユーザーのカバーレターを書きます。ルール:

1. 3 段落。合計約 200 ワード。最大 220。
2. 段落 1 (約 50 ワード): ユーザーが **この** 会社に書く具体的な理由で開く。
   製品、人物、最近のローンチ、または実際に考えた問題に言及。
   決して「I am writing to apply for the position of」で開かない。
3. 段落 2 (約 100 ワード): ユーザーの経験を JD にマッピングする 1 つの具体的ストーリー。
   具体的な結果。レジュメの再録ではない。
4. 段落 3 (約 50 ワード): 明確な次のステップで締める。傲慢でない自信。
   「I would love the opportunity to discuss」禁止。
5. 声: ユーザーが書いたように聞こえる。スタートアップではやや砕けて、
   ファイナンスやエンタープライズではややフォーマルに。プレスリリースでない。
   謙遜自慢でない。
6. バズワード禁止 (passionate、results-driven、fast-paced、dynamic)。
7. 「transferable skills」フレーミング禁止。仕事を見せるだけ。

カバーレターのみ出力。コメントなし。
```

### 入力形状

```
[ターゲット役職]
タイトル、会社、1 行で何をしているか。

[具体的なフック]
この会社についてリードする 1 つのこと。ちょうど 1 つ選ぶ。
例:
- 「御社の製品を 18 か月使ってきました — このカテゴリーで実ケイデンスで
  出荷する唯一のツールです。」
- 「<前職> で同様の決済問題に取り組み、次の 4 年はそれを深く
  掘りたいと考えています。」
- 「<採用マネージャー名> の書き物を何年も追っており、チームの
  最近のイベント駆動アーキテクチャの投稿が、私が誤解していた点を
  明確にしてくれました。」

[マッピングしたストーリー]
1 つのプロジェクト、文脈 2〜3 文、結果。

[締めのエネルギー]
自信あり、応じる、低圧。
```

### 出力例

**入力:**

```
[ターゲット役職]
Senior Backend Engineer, Payments — Lumenari Co (AI ツーリングマーケットプレイス、
月約 $2M トランザクション)

[具体的なフック]
「過去 3 年、同様の取扱高のマーケットプレイスで Stripe Connect + Postgres
の決済スタックを構築してきました。御社の最近のエンジニアリングブログ記事の
冪等な Webhook リトライは、まさに私がチームに推進してきたアーキテクチャの方向です。」

[マッピングしたストーリー]
Acme で、月約 $4M を処理する決済サブシステムを所有。idempotency キー +
デッドレターキュー追加で Webhook リトライ失敗を 78% 削減。
ミッドレベルエンジニア 2 名をメンタリング、18 か月で両名をシニアに昇格。

[締めのエネルギー]
今週か来週話せる。retry-failure の作業について有用なら詳しく共有可。
```

**AI が返す出力:**

```
Maya 様

御社の冪等な Webhook リトライに関するエンジニアリング投稿は、過去 1 年
私がチームに推進してきたアーキテクチャの方向そのものです — その次の
レイヤーの出荷をお手伝いできると思い、ご連絡しました。

過去 3 年、Acme Co で月約 $4M のトランザクションを行うマーケットプレイス
の Stripe + Postgres 決済スタックを所有してきました。最も誇る仕事:
6 か月で idempotency キーとデッドレターキューを導入し、Webhook リトライ
失敗を 78% 削減。さらにオンコールローテーションを硬化させ、P1 ページ
件数を月 12 件から 3 件に落としました。その過程でミッドレベルエンジニア
2 名をメンタリングし、現在は両名ともシニアです。メンタリングの部分が、
私が転職を考える理由の一つ — 次の役職ではそれを公式化したいと思います。

今週か来週でお話しできます。会話の前に retry-failure アーキテクチャの
詳細を共有することが有用であれば、喜んで。

— Alex
```

このレターが正しく行うこと:

- 会社のエンジニアリングコンテンツへの具体的な言及で開く。採用マネージャーは、あなたが本当に読んだことを知る。
- 本文段落はツール、数値、結果を名指す — レジュメの再録ではない。
- ユーザーの声でメンタリングに言及（「メンタリングの部分が、私が転職を考える理由の一つ」）、JD が明示的に求めているから。
- 応じる姿勢とソフトオファー（retry-failure アーキテクチャ）で締め。「I would love the opportunity」なし。

## パート 2 — LinkedIn リライト

3 つのセクションが重要、順に: ヘッドライン、About セクション、Experience 冒頭。

### ヘッドライン（最大 120 文字）

検索結果でリクルーターが見るもの。

**悪い:**

```
Senior Software Engineer | Passionate Builder | AWS / TypeScript / React
```

**より良い:**

```
Senior Backend Engineer — payments, Stripe, Postgres | Mentor | Calgary / Remote
```

プロンプトが強制するルール:

1. 現職と異なるなら、現職でなく狙う役職でリード。
2. 次に 3 つの具体的キーワード — テックスタックサラダではなく本当に使うツール。
3. 任意の第三セグメント: 所在地または可用性（「Open to remote NA」）。
4. バズワード禁止。「Passionate Builder」「Code Slinger」「Tech Enthusiast」禁止。

### About セクション — 最初の 3 行がすべて

「...see more」が切れる前に見えるのは最初の約 210 文字のみ。そこを最適化。

**プロンプト:**

```
ユーザーの LinkedIn About セクションを書きます。ルール:

1. 最初の文 (最大約 140 文字): ポジションステートメント。何をするか、誰のために、
   1 つの結果。多くのリクルーターが読むのはこの 1 行だけ。
2. 次の 2 文は合計約 210 文字以内に収める。読み手を「see more」クリックへ
   フック。
3. 全体長: 4〜6 個の短い段落、約 150 ワード。
4. 一人称、会話調。PR 担当でなくユーザーが書いたように聞こえる。
5. 1 つの具体的な CTA で締める:「X を採用していれば DM」「<リンク> で Y について書いている」
   「決済領域のシニアバックエンド役職に開いている」。
```

**出力例:**

```
マーケットプレイス向けに決済インフラを構築しています。過去 3 年、
Acme Co で月 $4M を処理する Stripe + Postgres スタックを所有 —
Webhooks、オンコール、メンタリング、全部です。

Acme の前はフィンテックスタートアップで、すべての決済エンジニアが
痛い目を見て学ぶ教訓を学びました: 冪等性はオプションではない、
デッドレターキューはオプションではない、runbook は午前 2 時に
書いていない誰かに読まれます。

役職で気にする 3 つ:
- 実ユーザーのいる難しい問題
- メンタリングが双方向に効くチーム
- 演劇なしで出荷する自律性

現在 Calgary、北米のリモート役職に開いています。決済領域の
シニアバックエンドを採用していれば DM ください — 行き先には
こだわりがあり、礼儀正しい 10 件より良い 1 件の会話を望みます。
```

最初の 210 文字（約 3 行）に見えるもの:

```
マーケットプレイス向けに決済インフラを構築しています。過去 3 年、
Acme Co で月 $4M を処理する Stripe + Postgres スタックを所有 —
Webhooks、オンコール、メンタリング、全部です。
```

それがフック。リクルーターは最初の段落で役職、ツール、結果を見て、続きを読むか判断。

### Experience セクション — 現職と直近職の冒頭

LinkedIn は誰かが expand をクリックしない限り、役職あたり 2〜3 行で切ります。なので各役職の最初の 2 行はレジュメの上 3 分の 1 に相当。

**プロンプト:**

```
LinkedIn 上のユーザーの現職の最初の 2〜3 個の箇条書きをリライト。
ルール:

1. 最初の箇条書き: この役職でのスコープとインパクトの 1 行サマリー。
2. 第二の箇条書き: ユーザーが狙う役職に最も関連する単一の実績。
3. 第三の箇条書き (任意): 幅を示す第二の実績。
4. レジュメと同じスタイルルール: 能動態、具体的数値、バズワードなし、
   JD 整合の語彙。
5. LinkedIn フォーマット済みテキストのみ出力。
```

出力例:

```
Senior Backend Engineer at Acme Co
2022 - 現在 · Calgary, AB (リモート)

→ 月約 $4M トランザクションのマーケットプレイス向けに決済と
  Webhooks サブシステム (Stripe + Postgres + Kafka) を所有。
→ idempotency キーとデッドレターキューを導入し Webhook リトライ
  失敗を 78% 削減、6 か月で P1 ページを 75% 減。
→ ミッドレベルエンジニア 2 名をメンタリング、18 か月で両名を
  シニアに昇格。
```

---

## 2 つの成果物がどう連動するか

カバーレターと LinkedIn の About セクションは同一ではないが、声とポジションを共有すべき。カバーレターで「マーケットプレイスで月 $4M の Stripe スタックを所有」と言うなら、LinkedIn About も同じことを言うべき — 表現を変えて。両方を読むリクルーターは、別人のように聞こえると気付く。

カバーレタープロンプトと LinkedIn-About プロンプトを同じチャットで連続して実行。AI が声の一貫性を保ちます。

---

## プロンプトがブロックするアンチパターン

- 「I am writing to apply for the position of [役職].」 — 見つけ次第削除。
- 「I am thrilled by the opportunity to...」 — 削除。
- 「Please find attached my résumé.」 — 知っている。削除。
- 「I would love the opportunity to discuss how my skills...」 — 削除。
- LinkedIn ヘッドラインの「Tech Enthusiast | Lifelong Learner | Coffee Addict」 — 削除。
- 「Results-driven, detail-oriented self-starter passionate about...」 — 全部削除。

どれかがすり抜けたら、プロンプト:「このドラフトからすべてのクリシェを剥がし、平易な言葉でリライト」。
