# メモリ — TypeScript + Next.js プロダクションパック

## ドメインコンテキスト

あなたは、Next.js App Router + Supabase + Vercel でプロダクション SaaS を出荷している開発者とペアを組んでいます。日々の作業は概ね、新機能をエンドツーエンドで作る、顧客が見つけたバグを直す、半年前は動いていたが今日のトラフィックに耐えないコードをリファクタリングする — のミックスです。ユーザーは多くの場合ひとり、もしくはほぼひとり。賢いが壊れやすいコードに付き合う時間はありません。3 か月後の自分も理解できるコードのための時間はあります。

スプリントは週次。毎週の大仕事は通常 1〜2 個のユーザー向け機能。見えない仕事はマイグレーション、モニタリング、そして全体が溶けないように支える地味なインフラ。成功とはこういう状態です: ビルドモード中は 1 日 1 つの PR、午前 2 時に Sentry のアラートが鳴らない、顧客はデプロイに気づかない。

コードベースはお馴染みの弧を描いて成長します: ルート 10 個なら問題なし、30 個になるとフィーチャーフォルダが必要、80 個になるとルートグループ + 共有レイアウト + サーバーレンダリング vs クライアントレンダリングの監査が必要。

## AI が知っておくべき用語

- **App Router**: Next.js 13+ の `app/` 配下のファイルベースルーティング。Pages Router の置き換え。
- **RSC**: React Server Component。App Router のデフォルト。サーバー側でレンダリングされ、クライアントには JS が送られない。
- **Server Action**: `"use server"` でマークされた関数。サーバー側で実行され、クライアントコンポーネントから呼び出せる。
- **Route Handler**: HTTP エンドポイント用に GET/POST 等をエクスポートする `app/api/.../route.ts`。
- **RLS**: Row Level Security。ポリシーで行単位のアクセスを強制する Postgres 機能。
- **Edge Function**: Vercel のエッジネットワークまたは Supabase Edge ランタイムで動作するコード。
- **Hydration**: クライアントの React がサーバーレンダリング HTML を引き継ぎ、イベントハンドラーをアタッチする処理。
- **Streaming**: サーバー側でレンダーされた順にページの一部をブラウザへ送ること。
- **Suspense**: データ読み込み中にストリーミングとフォールバック表示を可能にする React の境界。
- **Middleware**: プロジェクトルートの `middleware.ts` — レンダリング前、各リクエストで実行される。
- **ISR**: Incremental Static Regeneration — スケジュールまたはオンデマンドで再ビルドされる静的ページ。
- **PPR**: Partial Prerendering — 1 つのルート内で静的 + 動的を混在させる Next.js 15 の機能。

## よくあるワークフロー

- **グリーンフィールド SaaS の立ち上げ**: `create-next-app` → Supabase + Stripe SDK のインストール → キットのスキーママイグレーションを書く → `lib/supabase-server.ts` + `lib/supabase-service.ts` を配線 → `(auth)` ルートグループを追加 → 最初の保護ページ。
- **既存フォームへのサーバーアクション追加**: `schemas.ts` に Zod スキーマを定義 → `actions.ts` に `ActionResult` 形式のアクションを書く → フォームの `onSubmit` を `useActionState` に置き換える。
- **Pages Router を App Router にページ単位で移行**: トラフィックの少ないルートを 1 つ選ぶ → `app/` 配下に App Router 版を作成 → プレビューでスモークテスト → 準備ができたら切り替える。一括移行は試みない。
- **Hydration ミスマッチのデバッグ**: サーバーコンポーネント内の `Date.now()`、`Math.random()`、`window.*` を確認 → クライアントコンポーネントに移す → 必要なら `suppressHydrationWarning` で抑制（最終手段、理由を文書化）。
- **本番デプロイのチェックリスト**: typecheck クリーン → build クリーン → Vercel に ENV 変数が設定済み → Supabase マイグレーション適用済み → Stripe webhook シークレットを固定 → プレビューでエンドツーエンドのテスト。

## 避けるべきこと / よくある誤り

- **クライアントバンドルへの service-role キー混入**: `"use server"` が付いているものは OK。それ以外は、誤ってクライアントから import されることを防ぐために `"server-only"` の import が必要。
- **revalidate を伴わないクライアントからのサーバーアクション呼び出し**: 見た目は問題ないが、数クリックでデータが古くなる。常に `revalidatePath()` または `revalidateTag()` を呼ぶ。
- **認証ルートで `cache: 'no-store'` のない `fetch`**: Next がユーザー間でレスポンスをキャッシュする。意図しないデータ漏洩。
- **すべてのエラーを汎用メッセージで catch する**: 「問題が発生しました」の 500 はユーザーに何も伝えない。バリデーションエラー（return）、システムエラー（throw）、想定された不在（return null）を区別する。
- **マイグレーションを飛ばして Supabase ダッシュボードで編集する**: 1 回は動く。翌日にステージングが壊れる。マイグレーション一択。
