# メモリ — Python データ分析パック

## ドメインコンテキスト

データアナリストやデータサイエンティストは、1 日の大半をノートブックの中で過ごし、4 つのフェーズを行き来します: データの読み込み、クリーンアップ、変換、結果の伝達。ノートブックは Jupyter または Python 拡張機能付きの VS Code。データはウェアハウス（Snowflake、BigQuery、Redshift）、ローカルファイル（Parquet、CSV）、API のいずれか。出力は時にチャート、しばしば表、ときどきステークホルダー向けの読み上げ用回帰係数表。

苦労: 要件は曖昧に届く（「Q4 売上が下がった理由を調べてくれる?」）、データはスキーマドキュメントが示すより汚く、結論は既にカレンダーに入っている 15 分のミーティングに収める必要がある。スピードと信頼が優雅さより重要。今日 80% 正しいクエリは、月曜の完璧なクエリに勝る。

仕事は概ねアドホック分析（単発の質問）、定期レポート（週次メトリクス、月次 KPI）、モデリング（回帰、分類、たまに予測）に分かれる。今やほとんどのアナリストはノートブックの少なくとも半分を AI とペアでコーディングしている — AI は pandas API の想起が自分より速く、「やりたいことを記述、ドラフトを得る、AI が間違えた部分を直す」のループはゼロから書くより速い。

## AI が知っておくべき用語

- **DataFrame**: 表形式データ、pandas の中心型。行 + 名前付きカラム + インデックス。
- **Series**: 単一のカラム（1D）、インデックス付き。`df["col"]` が Series を返す。
- **Index**: 行識別子。通常 `RangeIndex`（0、1、2...）だが `DatetimeIndex`、`MultiIndex` などにもなる。
- **EDA**: Exploratory Data Analysis（探索的データ分析）。最初のパス — 形状、null、分布、外れ値。
- **OLS**: Ordinary Least Squares（通常最小二乗）。標準的な線形回帰。
- **p 値**: 帰無仮説が真であるときにこの結果以上を見る確率。慣習的に 0.05 未満で「統計的に有意」。常に誤用される。
- **効果量**: 統計的に有意かどうかとは別に、差が*どれだけ大きい*か。平均には Cohen's d、カテゴリにはオッズ比。
- **Window 関数**: 行を畳まない集約。`ROW_NUMBER`、`LAG`、`SUM OVER`。SQL と同じ。
- **Long vs. wide フォーマット**: long = 1 観測あたり 1 行、カテゴリカラム付き。Wide = ピボット済み、カテゴリごとに 1 カラム。Plotly と seaborn は long を好む。
- **Tidy data**: 各変数が 1 カラム、各観測が 1 行。Hadley Wickham の用語。有用なデフォルト。
- **DuckDB**: in-process 分析データベース。SQL で DataFrame や Parquet ファイルにクエリ。速い。
- **Polars**: Rust ベースの DataFrame ライブラリ。多くの操作で pandas より速い、若干異なる API（デフォルトで遅延、式ベース）。
- **ベクトル化**: 1 行ずつではなく、カラム全体に対する操作。常に `.apply` や `for` ループより速い。
- **ノートブック再起動**: すべての変数をクリアして上から下まで再実行。ノートブックが実際に動くと確信する唯一の方法。

## よくあるワークフロー

- **ステークホルダーからのアドホック質問**: 質問を注意深く読む → 関連するテーブルを引く → EDA ブロック → 文字どおりの質問に答える → 質問の裏にある質問を探す → 3 つのブレットで要約を書く。
- **週次メトリクスダッシュボードの構築**: DuckDB で集約用 SQL → 派生メトリクス用の小さな DataFrame → チャート用 Plotly → HTML に保存またはダッシュボードツールに送信。
- **A/B テスト分析**: 両 arm のイベントを引く → サンプルサイズと arm のバランスをチェック → プライマリー指標: t 検定または Mann-Whitney → セカンダリー指標: 同様 → 効果量 + 信頼区間を報告、p 値だけではない。
- **ステークホルダー向け回帰の fit**: 特徴量を準備（ワンホット、スケール、欠損処理） → OLS または logistic を fit → 残差を確認 → 普通の日本語で解釈を書く（「X が 1 増えると Y が 3.2 単位増える」）。
- **API エクスポートからのデータセットクリーンアップ**: ロード → カラム名を標準化 → dtype を修正 → 欠損を特定し決定 → 重複を処理 → 次の人が作業を繰り返さないよう `data_dictionary.md` を書く。

## 避けるべきこと / よくある誤り

- ベクトル化可能なものに `df.apply(lambda x: ...)` を使う。遅く、ベクトル化版より読みにくい。
- `.iterrows()`。常にベクトル化操作より遅い。最終手段または極小 DataFrame でのみ使う。
- `df.dropna()` で null をサイレントにドロップする。常に何がドロップされたかを先に示す。`df.isna().sum()` で前を確認、決定を文書化。
- p 値のみ報告する。p が 0.0001 で効果量 0.01 は統計的に有意で実用的には無意味。
- 6 スライス以上の円グラフ。棒グラフを使う。
- 3D 何か。3D 棒グラフは「可視化を真面目に考えていません」の名刺。
- 連鎖インデックス: `df["col"][df["col"] > 5] = ...`。`.loc[]` を使う。`SettingWithCopyWarning` は本物。
- セルを順不同に再実行して結果を信用する。restart-and-run-all できないなら、実際には分析を持っていない。
- ループ内で `concat` を使う。リストを作り、1 度だけ concat する。各 `concat` がすべてをコピーする。

## トーン / レジスター

実際のデータアナリストは具体的に話す。「`user_id` で join したら、50k から 47k 行になった — 3k 行が孤児、確認が必要」。カラム名をバッククォートで参照する。*データ*と*結論*を区別する。自分でプロファイリングしていないデータセットに体質的に懐疑的。「回帰は分散の 12% を説明する」と言い、「回帰は頑健」とは言わない。p 値*と*効果量を引用する。「データが物語を語る」とは言わない — データはパターンを示し、アナリストが物語を書く。「サンプルサイズ X」より「n=X」を好む。データが答えられない質問を聞くステークホルダーに対し、答えられるフリのチャートを捏造するよりも、優しく押し返す。
