# ステークホルダー更新テンプレート

> 3 つの味、同じ骨格: エグゼクティブブリーフ、エンジニアリング詳細、顧客向け。同じ週の仕事を 3 つの異なる読者向けに圧縮。

---

## 骨格（3 つの味すべてが共有）

1. **ステータス** — 一語（緑 / 黄 / 赤）+ 1 文
2. **出荷したもの** — 機能でなく結果
3. **次** — 次サイクルのコミット済み項目
4. **リスク** — 滑りうるものに正直に
5. **依頼** — この読者から必要な 1 つの具体的事項

味の違い:

- **長さ:** 200 / 400 / 150 ワード
- **語彙:** エグゼクティブとエンジニア向けでは社内ジャーゴン OK、顧客向けでは絶対なし
- **ブロッカーの深さ:** エグゼクティブはヘッドライン、エンジニアは詳細、顧客向けは通常省略
- **依頼:** エグゼクティブは判断 / ヘッドカウント / 紹介、エンジニアは優先順位付け / アンブロック、顧客はフィードバックまたはベータ参加

---

## 味 1 — エグゼクティブブリーフ（約 200 ワード）

### プロンプト

```
エグゼクティブステークホルダー更新を書きます。ルール:

1. 約 200 ワード。ハードキャップ: 250。
2. 一語のステータスで先頭: 緑 / 黄 / 赤。その後に理由を 1 文。
3. 「出荷したもの」は機能でなく結果。「『ビューを失った』チケットを 30 日で
   47% 削減」、「Saved Searches v1 を出荷」ではない。
4. 「リスク」は正直に。滑りうるなら、その理由を言う。
5. 1 つの具体的依頼で終える。「Y までに X の判断が必要」。「質問があれば
   お知らせください」ではない。
6. 「I hope this email finds you well」禁止。「circling back」禁止。
7. 声: 直接的、落ち着いた、具体的。数値があれば数値。

更新のみ出力。
```

### 出力例

```
**ステータス: 黄** — Saved Searches は 5 月 30 日ローンチで順調、
オンボーディング作業はエッジケース発見により約 2 週間遅延。

**今期出荷**
- Webhook リトライ失敗を 78% 削減 (長年の P1 インシデントカテゴリーを解消)
- トップ 3 ダッシュボードフローのモバイルウェブ同等性
- 新初回タッチツールチップ実験でアクティベーション +3pp

**次 (今後 2 週間)**
- Saved Searches v1 → 5 月 30 日出荷、まず 4 顧客でベータ
- オンボーディング改訂 v2 → 新エッジケース反映で調整
- チーム共有保存 → 5 月 28 日キックオフ (<顧客 X> 更新でコミット済み)

**リスク**
- オンボーディング完了目標 (+10pp) — 初回フローのエッジケースにより
  Q2 から Q3 序盤へ後ろ倒し。緩和策: 高影響エッジを含む v2 を出荷、
  残りは Q3。
- 残り 2 フローのモバイルウェブ同等性は、失ったエンジニアシートを
  補充しない限り Q4 に滑る。

**依頼**
オープンエンジニアシートを補充するか、モバイルウェブの Q4 滑りを受け入れる
かの判断が金曜までに必要。どちらの道も機能する、来週のチーム計画に
曖昧さを持ち込みたくない。
```

何が起きているか:

- ステータスは緑ではなく黄。PM は正直。
- 「出荷したもの」は 3 行、各々が数値付き結果。
- 「リスク」は緩和策付きの実リスク、定型文ではない。
- 依頼は具体的 — 判断、日付、オプション提示。

約 200 ワード。エグゼクティブは 45 秒でスキャンできます。

## 味 2 — エンジニアリング詳細（約 400 ワード）

### プロンプト

```
エンジニアリングチーム向けステークホルダー更新を書きます。ルール:

1. 約 400 ワード。ハードキャップ: 500。
2. エグゼクティブブリーフと同じ骨格、ただし以下を含む:
   - ブロッカー (技術的または組織的)、提案パス付き
   - 他チームへの依存関係
   - チームが求めている判断、オプション + 推奨付き
3. 技術的語彙は OK。エンジニアリング向けに薄めない。
4. 同じ「ステータスで先頭」の規律。黄は黄。
5. 依頼で終える。エンジニアリング関連: 優先順位付けコール、アンブロック、
   トレードオフ判断。

更新のみ出力。
```

### 出力例

```
**ステータス: 黄** — Saved Searches は 5 月 30 日順調、オンボーディング
作業は約 2 週間遅延、クロスチーム依存関係 1 つがリスク。

**今期出荷（結果 + どう）**
- Webhook リトライ失敗 78% 削減: idempotency キー + デッドレターキューを
  導入。Stripe サポートが彼らの推奨と整合するパターンと確認。P1 ページ
  件数 12/月 → 3/月。
- トップ 3 フローのモバイルウェブ同等性: ダッシュボードレイアウト
  プリミティブを CSS Grid 使用にリファクタ、副作用として長年のタブレット
  ブレークポイントバグを解消。
- アクティベーション +3pp: 初回タッチツールチップの A/B テストが 95% 信頼度
  で終了。バリアント B (挨拶でなく文脈的) が勝利。

**現在構築中**
- Saved Searches v1 — バックエンド完了、UI 80%。フィルター JSON ストレージ
  パターンを使用頻度上位 12 のクエリ形状に対して検証。ベータコホート選定:
  4 顧客、すべてパワーユーザー、オプトイン。
- オンボーディング v2 改訂 — 高影響エッジを先に出荷するためにスコープ調整。
  3 つのエッジケースを Q3 に残す。

**ブロッカーと依存関係**
- チーム共有保存のキックオフは Permissions チームの新 RBAC プリミティブ
  出荷 (ETA: 5 月 25 日) に依存。毎週追跡。フォールバック: より単純な
  全か無かの共有モデルでチーム共有保存を出荷、RBAC 着地時に細粒度に
  リファクタ。
- 検索バックエンド p95 レイテンシが Q1 で 18% 上昇 — まだユーザー影響なし、
  トレンドあり。Q3 の火事になる前に、エンジニア 1 週間で調査することを提案。

**必要な判断**
1. Q2 でオープンエンジニアシートを補充するか、モバイルウェブの Q4 滑りを
   受け入れるか？ 推奨: 補充。モバイルウェブは H2 のトップ更新顧客依頼
   4 件中 2 件に含まれる。
2. RBAC が滑る場合、全か無かの共有モデルでチーム共有保存をフォールバック
   するか？ 推奨: yes。顧客コミットメントは Q3、RBAC 着地時のリファクタ
   コストは約 3 日。

**依頼**
上記 2 件の判断が金曜までに必要。両方が次スプリント計画を形作る。
```

エグゼクティブブリーフとの違い:

- 結果だけでなく、どう出荷したかを含む。
- まだユーザー影響していないレイテンシトレンドを浮上 — エンジニアリングシグナルで、エグゼクティブシグナルではない。
- 判断をオープン質問でなくオプション + 推奨付きでフレーム。
- 依頼は具体的判断と日付を名指す。

## 味 3 — 顧客向け（約 150 ワード）

### プロンプト

```
顧客向け更新を書きます。ルール:

1. 約 150 ワード。ハードキャップ: 200。
2. 平易な言葉。社内ジャーゴン禁止。顧客に関係ないメトリクス言及禁止。
3. 顧客が今使えるもの (出荷したもの) で先頭。
4. 「次」は最大月粒度。正確な日付へのコミットメントなし。
5. フィードバック用に 1 つのチャネル。使いやすく。
6. ステータスカラーなし。「リスク」言葉なし。顧客にとって重要なら、
   ポジティブにフレームするか省略。
7. 声: 温かいがおだてない。自信ありだが押し付けない。

更新のみ出力。
```

### 出力例

```
皆さま、

今月ダッシュボードに何が新しく、次に何が来るかの簡単なメモです。

**今使えるもの**
- パワーユーザー向けに「このビューを保存」ボタンがダッシュボードで利用可能。
  フィルタービューを保存、命名すれば、URL 構造が裏で変わっても必ず正確に
  復元します。ユーザーあたり 50 件まで。
- モバイルウェブが、最もよく使う 3 つのフロー (ダッシュボード、アラート、
  監査ログ) で使えるようになりました。残り 2 フローは今秋です。

**次**
- チーム共有保存ビュー — チームとフィルタービューを共有。7 月目標。
- オンボーディングする新チームメイトの初回体験を改善。6 月下旬。

**小さな依頼**
保存ビューを試して何か欠けている / 変な点があれば、このメールに返信
ください。すべて自分で読み、次に何を作るかを形作ります。

— Alex
```

違い:

- ステータスカラーなし、「リスク」フレームなし。
- 「ユーザーあたり 50 件」は実限度を浮上、ただし顧客言葉で。
- 「次」は四半期や具体日付でなく月を使う。
- 依頼は直接的で簡単（このメールに返信）。

## 1 つのワークフローで 3 つすべてを使う方法

多くの週で、エンジニアリング詳細更新を先に書く理由は、そこに原材料が住むから — スプリント計画、ブロッカー、チームの判断。その後圧縮します。

ワークフロー:

1. エンジニアリング詳細更新を書く（約 400 ワード）。
2. AI に通す:「エグゼクティブブリーフ用に 200 ワードに圧縮。具体的依頼を 1 つ残す。技術語彙を落とす」。
3. AI に再度通す:「顧客向けに 150 ワードでリライト。平易な言葉。社内ブロッカーを落とす。今使えるものを軸にフレーム」。

合計時間: 3 版で 30 分。圧縮パスが過剰主張を捕まえる — エグゼクティブ版がヘッジなしで「X を出荷した」と言えないなら、エンジニア版もおそらく過剰主張している。

---

## プロンプトがブロックするアンチパターン

- 「I hope this email finds you well.」 — 削除。
- 「Just wanted to circle back on...」 — 削除。
- 「Per my last email...」 — 削除。
- 「We continue to make progress on...」 — 曖昧。結果と数値で置換。
- 「Things are going well!」 — ステータスは色で、感情ではない。1 つ選ぶ。
- 「Let me know if you have any questions.」 — 依頼ではない。実際の依頼を明示する。
- 「Excited to share...」 — エグゼクティブはあなたの感情を知る必要なし。実質に入る。

どれかがすり抜けたら、プロンプト:「すべての詰め物語句を剥がし、ステータス、結果、依頼でリライト」。
