# PRD + ロードマップテンプレート

> 80% の場面で使う PRD の形、加えて散らかったバックログを優先度付きバケットに変える Now/Next/Later ロードマップドラフター。

---

## パート 1 — PRD

### 形

```
# PRD — <機能名> (v0.x, <著者>, <日付>)

## 問題
何が壊れているか、誰のために、平易な言葉で。可能ならユーザーを引用。

## 目標
この仕事の目指す 1 つの結果。1 文。

## 非目標
これが **やらない** ことの明示的リスト。項目ごとの理由 (「Phase 2」「別ワーク
ストリーム」「気にするメトリクスを動かさない」)。

## 成功メトリクス
機能したことをどう知るか。目標数値。時間枠。

## 受入基準
「完了」の姿。箇条書き、テスト可能。

## スコープ
**含む:** 構築するスライス
**除く:** 明示的な切り捨て
**ストレッチ:** 時間が許せば

## 未解決の問い
まだ知らないこと。各々に締切またはオーナー。
```

それだけ。ミッションステートメントなし。実際に荷を背負わない限り競合分析セクションなし。チームがすでにユーザーを知っているなら「ユーザーペルソナ」詰め物なし。

### プロンプト

```
PRD をドラフトします。ルール:

1. ドキュメント長は機能規模に合わせる。2 日でできる機能は 1 ページ PRD。
   2 四半期のイニシアチブは 3〜5 ページ。小さな仕事に 12 ページ PRD はなし。
2. 上記の形を順に使う: 問題 → 目標 → 非目標 → 成功メトリクス → 受入基準
   → スコープ → 未解決の問い。
3. 非目標セクションは必須で、本当に仕事をする。各項目に 1 行の理由。
   非目標が実は Phase 2 判断なら、未解決の問いセクションにリンク。
4. 成功メトリクスは数値と時間枠を持つ。「アダプションが増加」はメトリック
   ではない。「WAU の 25% が 60 日以内に保存済み検索を作成」がメトリック。
5. 受入基準は箇条書き、テスト可能、エンジニアが定義済みとして使えるよう
   に書く。
6. スコープは In / Out / Stretch を持つ。Out リストが事前に「でも〜は？」
   を抑える。
7. 未解決の問いには決定者または締切を名指す。「TBD」では足りない。
8. 声: 直接的、具体的、やや疲れている。「leverage」「unlock」「double down」
   「transform」禁止。「I hope this finds you well」禁止。

PRD のみ出力。求めない限りコメントなし。
```

### 入力形状

```
[仕事]
機能: <名前>
ターゲットユーザー: <誰> (具体的に — 役割、顧客規模、セグメント)

[ステータス / コンテキスト]
段階: アイデア / スケッチ / 構築 / 出荷
シグナル: リサーチ / チケット / エグゼクティブ推進 / メトリクストレンド / 競合
PRD の読者: エンジニア / リーダーシップ / セールス

[原材料]
箇条書き、Slack スレッド、会議メモ、過去の PRD。未整形で OK。

[制約]
- ドキュメント長
- トーン
- すでに下された決定 (蒸し返さない)
- 明示的にまだ下されていない決定 (未解決の問いとしてフラグ)
```

---

### 出力例 — 「保存済み検索」PRD

**入力:**

```
[仕事]
機能: SaaS ダッシュボードの保存済み検索
ターゲットユーザー: パワーユーザー — 顧客側の ops と analytics の役割、
通常はダッシュボードを日次で使う 10〜50 名チーム。

[ステータス / コンテキスト]
段階: スケッチ。8 週間で 6 件の顧客コール、同期間 12 件のサポートチケット
で聞いた。デザインはまだなし。
読者: エンジニアリングリード + IC エンジニア 2 名 + デザイン。

[原材料]
- 顧客はフィルター済みビューを保存して戻りたい
- 名前を付けたい
- チームと共有したい (一部、全員ではない)
- 結果が変わったら通知されたい (一部、全員ではない)
- 一部は API、大半は UI 経由で依頼
- 現行回避策: クエリパラメータ付き URL をブックマーク — 脆弱、URL 構造
  変更で壊れる

[制約]
- 1〜2 ページ
- トーン: スクラッピー、社内向け
- 決定済み: 別ページでなくダッシュボード内
- 決定済み: パーソナル保存先、チーム共有は Phase 2
- 未解決: 結果変化時の通知 — Phase 1 か 2 か？
```

**出力（抜粋）:**

```
# PRD — Saved Searches (v0.5, Alex, 2026-05-14)

## 問題
パワーユーザー — 顧客側の ops と analytics の役割 — は週に複数回同じ
フィルタークエリを実行する。今は URL をブックマークしているが、
クエリパラメータ構造を更新すると壊れる。過去 8 週間で 6 件の顧客コール
と 12 件のチケットで聞いた。

引用 (Maya、<顧客> の ops リード):「毎週月曜に同じフィルターを再構築
している。前回のリリース以降、ブックマークの半分が動かなくなったので
諦めた。」

## 目標
パワーユーザーの「フィルタービューを失った」摩擦を低減。具体的には:
ユーザーが名前付きフィルタービューを保存、戻り、(Phase 2) 共有できる
ようにする。

## 非目標
- チーム共有の保存済み検索 → Phase 2。未解決の問い参照。
- API ファーストの保存済み検索 → Phase 2。需要の大半は UI。
- プロダクト横断の保存済み検索 (ダッシュボード + レポート) → 範囲外、
  別ワークストリーム。
- 保存済み検索の分析 (どの保存が最も使われるか) → Phase 2。

## 成功メトリクス
- ローンチから 60 日以内に、週次アクティブダッシュボードユーザーの 25%
  が少なくとも 1 つの保存済み検索を作成
- 同 60 日枠で「ビューを失った」サポートチケットカテゴリーが 50% 減
  (ベースライン: 2026 年 Q1 で月約 24 件)
- アクティブパワーユーザーあたりの中央値保存済み検索 ≥2 を 30 日目に

## 受入基準
- ユーザーはダッシュボード内のワンクリック「このビューを保存」アクション
  で現在のフィルタービューを保存できる
- 保存済みビューは命名 (既定 = フィルター自動要約、ユーザー編集可)
- 保存済みビューは左レール「マイ保存ビュー」セクションに表示
- 再開すると URL 変更にかかわらず正確なフィルター状態を復元
- 保存済みビューは URL 文字列でなくフィルター JSON として保存
- ユーザーあたり最大 50 個、上限超過は明確なエラーを表示

## スコープ
**含む:** パーソナル保存、UI のみ、命名、復元可能。50/ユーザー上限。
**除く:** チーム共有。API。通知。プロダクト横断。
**ストレッチ:** 誤削除に備えたソフト削除 + 復元。

## 未解決の問い
1. 結果変化時の通知 → Phase 1 か 2 か？
   推奨: Phase 2。コア保存 / 復元ループには不要な変更検出レイヤーを追加。
   決定者: <PM>、2026-05-21 まで。
2. ユーザーあたりストレージ上限 — 50 が妥当に感じる、実データなし。
   エンジニアリングのストレージフィードバックに基づき調整可。
3. 基盤フィルター列が改名 / 削除された時のマイグレーションポリシー。
   決定者: <エンジニアリングリード> + <PM>、キックオフ前。
```

この PRD が行うこと:

- 問題セクションで実ユーザーを引用。
- 非目標が重労働 — 4 つの明示的切り捨て、それぞれに理由。
- 成功メトリクスに数値、ベースライン、時間枠。
- 受入基準はテスト可能。
- スコープの「除く」セクションが事前に「でも〜は？」質問を抑える。
- 未解決の問いに決定者と締切。

700 ワード、1〜2 ページ PRD。仕事に対して適切なサイズ。

## パート 2 — Now / Next / Later ロードマップ

### プロンプト

```
Now/Next/Later ロードマップを更新します。ルール:

1. 3 列: Now、Next、Later。それ以外なし。
2. 各項目は結果 (例:「『ビューを失った』チケットを 50% 削減」)、機能名
   ではない。機能名は括弧内。
3. 各項目に四半期と信頼度 (高 / 中 / 低)。信頼度は正直に。すべてを高に
   しない。
4. 「Now」= コミット済み、進行中。
5. 「Next」= 次サイクルにコミット済み。
6. 「Later」= レーダー上、未コミット。
7. ユーザーが対応する削減なしに Later から Now に項目を動かす提案を
   したら、押し戻す:「Now の何が出ていく？」
8. ロードマップを Markdown 表として出力。下に前サイクルからの変化を
   説明する 1 段落。

声: 直接的、具体的。四半期なしの「soon」禁止。曖昧な動詞禁止。
```

### 入力形状

```
[現在のロードマップ]
既存の Now / Next / Later を貼る、または口頭で記述。

[変わったこと]
- 追加される新イニシアチブ
- 出荷したイニシアチブ
- 滑っている / 優先度を下げるイニシアチブ
- 戦略的コンテキスト (顧客コミットメント、競合の動き、キャパシティ変化等)

[制約]
- 四半期ホライズン (1〜2 四半期が典型)
- チームキャパシティの現実 (前サイクルからの大きな変化はあるか？)
- 読者 (社内チーム、リーダーシップ、セールス向け)
```

### 出力例

**入力:**

```
[現在のロードマップ]
Now:
- オンボーディング完了 +10pp (改訂版初回フロー) — Q2 26、高
- 「ビューを失った」チケット 50% 削減 (Saved Searches v1) — Q2 26、高

Next:
- トップ 5 ダッシュボードフローのモバイルウェブ同等性 — Q3 26、中
- パワーユーザーリテンション +5pp (チーム共有保存 + API) — Q3 26、中

Later:
- 顧客側管理者向けのインプロダクト分析 — Q4 26、低
- 顧客エンジニア向け API レート制限ダッシュボード — Q4 26、低

[変わったこと]
- オンボーディング作業は順調だが、高でなく中に傾いている — 初回フローで
  想定以上のエッジケースを発見。
- トップ 3 顧客がチーム共有保存の Q3 出荷を条件に更新をコミット。早める
  必要がある。
- 今期エンジニアを 1 名失った。キャパシティ約 20% 減。

[制約]
- 2 四半期ホライズン
- 読者: リーダーシップ読み上げ
```

**出力:**

```
| バケット | 結果 | 四半期 | 信頼度 |
|--------|---------|---------|------------|
| Now    | 「ビューを失った」チケット 50% 削減 (Saved Searches v1)   | Q2 26 | 高 |
| Now    | オンボーディング完了 +10pp (初回フロー)                  | Q2 26 | 中 |
| Next   | パワーユーザーリテンション +5pp (チーム共有保存 + API)   | Q3 26 | 中 |
| Next   | トップ 5 ダッシュボードフローのモバイルウェブ同等性     | Q3 26 | 低 |
| Later  | 顧客側管理者向けのインプロダクト分析                    | Q4 26 | 低 |
| Later  | 顧客エンジニア向け API レート制限ダッシュボード         | Q4 26 | 低 |

**変わったこと:** オンボーディングは高から中信頼度に — 初回フローに想定
以上のエッジケース。チーム共有保存は Next (Q3) に残るが、トップ 3 顧客
の更新契約コミットメントになったため、Q3 ではモバイルウェブ同等性 (エンジニア
1 名喪失による約 20% キャパシティ低下で現在低信頼度) を犠牲にしてでも
優先。補充がなければ Q4 でモバイルウェブを再検討推奨。
```

この出力が行うこと:

- 信頼度について正直。新エッジケースのためオンボーディングを中に下げた。
- チーム共有保存を優先する理由として、顧客の更新条件を浮上。
- キャパシティ低下とその帰結を率直に呼び出し。
- トレードオフなしにチームが損失を吸収できるふりをしない。

## PRD をスキップするとき

すべての機能が PRD を必要とするわけではない。スキップする条件:

- 仕事が 2 日未満で、チームがすでにユーザーを理解している。
- 仕事がバグ修正または小さなリファクタリング。
- 仕事がデザイン文書で十分議論済みで、PRD はそれを要約するだけになる。

PRD をスキップしても成果物は残す: 代わりに「何 + なぜ + 機能したかをどう知るか」の 3 箇条書きを書く。小さな仕事でも書面の結果ステートメントから恩恵を受ける。
