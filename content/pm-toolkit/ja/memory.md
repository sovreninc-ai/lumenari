# メモリー — プロダクトマネージャーツールキット

## ドメインコンテキスト

プロダクトマネジメントは、ユーザーが欲しいもの、エンジニアリングが作れるもの、ビジネスが成長に必要とするものの間にある、地味な中間層。PM の仕事は不完全な情報下での意思決定: 何を、どの順序で、どんなトレードオフで作るか、機能したかをどう知るか。PM が出荷する成果物 — PRD、ロードマップ、スプリント計画、ステークホルダー更新、メトリクス読み上げ — は、それらの判断を可視で再検証可能にするために存在します。

典型的な週: 約 40% は会議（計画、レビュー、顧客コール、1on1、リーダーシップ読み上げ）、30% は執筆（スペック、更新、意思決定文書、フォローアップ Slack スレッド）、20% は顧客またはデータリサーチ、10% はその週のサプライズ。スタートアップの PM は執筆と顧客時間に傾く、大企業の PM は会議とステークホルダー管理に傾く。最も遠くまで届くアウトプットは書き物 — エグゼクティブはあなたの更新を電話で読み、セールス担当は商談であなたのロードマップを引用し、エンジニアはキックオフから数週後にあなたの PRD を参照する。明瞭に書くことが実際の仕事。

成功はこう見える: チームが会社が気にするメトリクスを動かす仕事を出荷、誰も驚かない程度に当初言ったタイムラインに近く出荷。失敗はこう見える: 機能を期日通り出荷したが、メトリクスは動かず、誰もその理由を説明できない。良い PM は、構築自体と同等のエネルギーを「機能したかどう知るか」「機能しなかった場合の次の実験は何か」に費やす。

## AI が知っておくべき語彙

- PRD: Product Requirements Document（プロダクト要件文書）。機能やイニシアチブのスペック。
- BRD: Business Requirements Document。古く、広く、現代のショップではあまり使われない。
- スペック: PRD または任意のデザイン文書の略語。
- Now/Next/Later: ロードマップフォーマット。3 バケット、四半期粒度を超える日付なし。
- OKR: Objectives and Key Results。目標設定フレームワーク。ツールとして有用、宗教ではない。
- KR: Key Result。OKR の測定可能な部分。
- North Star メトリック: チームまたは会社が向き合う単一のアウトプットメトリック。
- AARRR / Pirate Metrics: Acquisition、Activation、Retention、Referral、Revenue。クラシックなファネル。
- JTBD: Jobs-to-be-done。ユーザーがプロダクトを「雇って」何をさせるかを理解するフレームワーク。
- ICE: Impact、Confidence、Ease — 優先順位付けルーブリック。
- RICE: Reach、Impact、Confidence、Effort — より詳細な優先順位付けルーブリック。
- 受入基準: 「この機能は完了か」のチェックリスト。
- DoD: Definition of Done。すべてのストーリーに適用されるチームレベルの基準。
- DAU / WAU / MAU: Daily / Weekly / Monthly Active Users。
- アクティベーション: ユーザーが最初に意味のある価値の瞬間に到達すること。定義はプロダクト固有。
- リテンションカーブ: 時間経過に伴うコホートリテンション。フラットが目標、下降は離脱。
- LTV / CAC: Lifetime Value / Customer Acquisition Cost。成長が健全かを決める算数。
- NPS: Net Promoter Score。サーベイベースのロイヤリティメトリック。方向性として有用、荷を背負わない。
- ICP: Ideal Customer Profile。プロダクトが構築されている顧客像。
- スプリント、スタンドアップ、レトロ、リファインメント: スクラム語彙。チームが厳格でなくても使う。
- ベロシティ、キャパシティ、バーンダウン: 計画の算数。キャパシティは時間、ベロシティはストーリーポイントまたは出荷項目数。
- 繰越: 前スプリントで終わらなかった作業。明示的に管理、積み上げない。

## よくあるワークフロー

- **PRD を書く:** 問題 → 目標 → 非目標 → 成功メトリクス → 受入基準 → スコープ → 未解決の問い。非目標セクションが最も仕事をする — キックオフを脱線させる前に「でも X はどう」を抑える場所。
- **ロードマップを更新:** 現在の Now/Next/Later から開始、前四半期の実際の納品を見て、各項目の信頼度（高 / 中 / 低）を調整、バケット間で項目を移動、その後、変更点について 1 段落のコンテキストとともに再共有。
- **スプリントを計画:** 先にキャパシティ算数（名目時間から PTO、オンコール、会議を差し引く）、その後繰越トリアージ、その後 P0 / Stretch / Won't-do。スプリント目標を冒頭に 1 文で書く。
- **メトリクスレビューを実行:** 最も重要な 3〜5 個のメトリクスを選び、各々にトレンド / 比較対象 / 仮説 / フォローアップを書く。ノイズは埋める。
- **ステークホルダー更新を送る:** エンジニアリング詳細版（約 400 ワード）から開始、その後エグゼクティブブリーフ（約 200）と顧客向け（約 150）に圧縮。同内容、3 つの読者。
- **顧客フィードバックをトリアージ:** テーマでクラスター化、頻度をカウント、ICP 適合で重み付け、1 行結果付きでバックログに投入。

## 避けるべきこと / よくあるミス

- **PRD の肥大化。** 2 日でできる機能の 12 ページ PRD は、何が欲しいか分かっていないとエンジニアリングに伝える。ドキュメント長を機能規模に合わせる。
- **「Q3」精度のロードマップをコミットメントとして扱う。** 「Later」は「Later」の意味。実際に計画していない四半期を約束しない。
- **OKR カーゴカルト。** 設定すべき目標があるからではなく、会社が OKR を運用しているから OKR を設定する。もっと悪いのは: 実は測定不能な KR を書く。
- **1 つのメトリクスで十分とふりをする。** North Star は有用だが、多くのチームには 2〜4 個のメトリクスが必要 — 使用、アクティベーション、リテンション、売上 — 何が本当に起きているかを知るために。
- **「leverage」の文。** 「We need to leverage our existing user base to unlock new growth verticals.」 一語残らず削る。
- **顧客との会話の前に PRD を書く。** ユーザーを引用できないなら、まだ問題を知らない。
- **ステークホルダー更新の曖昧な依頼。** 「ご質問があればお知らせください」。それは依頼ではない。必要な判断、欲しい紹介を明示する。
- **ロードマップ項目を機能名と混同。** 「Build saved searches v1」は機能。「Cut 'lost my view' tickets 50%」は結果。ロードマップは結果に住む。

## トーン / レジスター

本物の PM は直接的、やや疲れている、しかも常に具体的に聞こえる。彼らは「ユーザーがこれを欲しい」（通常はノイズ）と「過去 8 週間で 12 件の顧客がこれを依頼」（シグナル）の違いを知る。仕事を過剰に売らない、数値とユーザー引用に持ち上げさせる。書き物では、短い文、可能なら名前付きユーザー、明示的な日付と件数を既定とする。曖昧な動詞にアレルギー: 「leverage」「unlock」「drive」「double down」「transform」。機能に「yes」と言うときは本気、「not now」と言うときも本気で、ひるまずに理由を説明できる。声は、プロダクトを出荷した人物のように聞こえるべきで、McKinsey デッキを読んでいる人物のようには聞こえてはいけない。
