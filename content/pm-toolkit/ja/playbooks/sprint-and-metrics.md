# スプリント計画 + メトリクスレビュー・プレイブック

> 正直なキャパシティ算数、1 行に収まるスプリント目標、人が実際に読む読み上げを生むメトリクスレビューフォーマット。

---

## パート 1 — スプリント計画

### 誰も正直にやらないキャパシティ算数

多くのチームが名目時間で計画し、未達の理由を不思議がる。機能する算数:

```
名目時間 = エンジニア × 時間 / 日 × スプリント日数
差し引く:
  - PTO と休日 (チーム合計)
  - オンコールローテーション (オンコールエンジニアの週の 10〜20%)
  - 定例会議 (典型的チームでエンジニアあたり週約 6 時間)
  - スピルオーバー / 保守 / 未計画 (残りの 10〜15%)

残り = 実際の新規作業キャパシティ
```

エンジニア 4 名、8 時間 / 日の 2 週間スプリントは名目で 320 時間。現実は実新規作業キャパシティで **140〜180 時間** に近い。スプリント計画が 320 を仮定していると、仕事の半分を次スプリントに繰り越します。

### プロンプト

```
私とスプリントを計画します。ルール:

1. キャパシティ算数で開始。チーム規模、スプリント長、既知の不在を伝えます。
   標準の差し引き (オンコール 15%、会議エンジニアあたり週約 6h、スピルオーバー
   12%) で名目 → 実キャパシティを計算してください。
2. その後、前スプリントからの繰越をトリアージ。各繰越項目: 残す、落とす、
   分割。
3. その後、新規作業を優先順位付け: P0 (必ず出荷)、Stretch (時間があれば)、
   Won't-do (このスプリントの明示的切り捨て)。
4. スプリント目標は冒頭に 1 文で。チームを知らない人にもきれいに読める。
5. スプリント計画を出力: スプリント目標 → キャパシティ → 繰越 → P0 →
   Stretch → Won't-do。
6. ストーリーポイントのカーゴカルトなし。すでにチームが使う時間または
   ラフサイジング (S/M/L/XL) を使う。

声: 直接的、具体的。計画は 60 秒でスキャン可能であるべき。
```

### 入力形状

```
[チーム]
エンジニア: <人数 + 有用なら名前>
デザイナー: <人数>
PM 時間: <週の比率>

[スプリント]
長さ: 1 週間 / 2 週間
開始: <日付>
終了: <日付>

[既知の不在]
- <エンジニア X>: 火〜水休
- <エンジニア Y>: 第 1 週まる休 (休暇)
- 今スプリントオンコール: <エンジニア Z>

[前スプリントからの繰越]
- <項目>: ステータス (50% 完了 / ブロック / 着手せず)

[今スプリントの候補作業]
- <項目>: あればラフサイジング
- <項目>: ...
```

### 出力例

**入力:**

```
[チーム]
エンジニア 4 名 (Alex、Beth、Carmen、Dev)
デザイナー 1 名 (Eli) — 今スプリントこのチームに 50%
PM: 私、約 30% キャパシティ

[スプリント]
2 週間、2026 年 5 月 19 日〜30 日

[既知の不在]
- Dev: 第 1 週の火〜水休 (3 日休)
- Beth: 第 2 週まる休 (休暇)
- オンコール: Carmen がスプリント全期間

[前スプリントからの繰越]
- Saved Searches v1 UI ポリッシュ (約 70% 完了、デザインレビュー待ちでブロック)
- Webhook リトライ可観測性ダッシュボード (約 50% 完了、リトライ失敗作業
  出荷時に優先度低下)

[今スプリントの候補作業]
- Saved Searches v1 ローンチ (UI ポリッシュ + ベータロールアウト)
- チーム共有保存バックエンド (RBAC 統合スパイク)
- 初回オンボーディング v2 (エッジケース修正 — 3 つの具体的バグ)
- 「Audit Log」ビューのモバイルウェブ
- 顧客共有保存 UX 探索 (デザイン探索のみ)
```

**出力:**

```
**スプリント目標:** 5 月 30 日までにベータコホート向けに Saved Searches v1
を出荷。次スプリント向けにチーム共有保存キックオフをアンブロック。

**キャパシティ**
- 名目: エンジニア 4 名 × 8h × 10 日 = 320h
- Beth 第 2 週休: −40h
- Dev 3 日休: −24h
- Carmen オンコール (スプリントを通して 15%): −12h
- 会議 (6h/週 × エンジニア 4 名 × 2 週): −48h
- スピルオーバー / 保守 (12%): −24h
- **実新規作業キャパシティ: 約 172h**

**繰越 (先に決める)**
- Saved Searches v1 UI ポリッシュ (約 70% 完了) → 残す。デザインレビュー
  は 5 月 20 日予定。今スプリントの P0。
- Webhook リトライ可観測性ダッシュボード → 落とす。元のリトライ失敗作業
  は出荷済み、ダッシュボードはもう高優先度ではない。ロードマップの
  Later へ移動。

**P0 (コミット — 約 140h に収まる)**
- Saved Searches v1 UI ポリッシュ + ベータロールアウト (Alex、約 40h)
- チーム共有保存 RBAC 統合スパイク (Beth が休暇前、Carmen が継続、約 50h)
- 初回オンボーディング v2 エッジケース修正 — 3 つの具体的バグ
  (Dev、約 30h)
- モバイルウェブ Audit Log ビュー (Carmen がオンコール作業の合間、約 20h)

**Stretch (P0 が早く終われば余裕 約 30h)**
- Eli と顧客共有保存 UX 探索 (デザイン、約 30h)
- 技術的負債: 検索バックエンドレイテンシ調査 (Alex が空いていれば)

**Won't-do (このスプリントの明示)**
- 顧客共有保存バックエンド作業 (RBAC スパイク結果待ち)
- Saved Searches の API (Phase 2 — 今サイクルのコミットメント外)
- Webhook リトライ可観測性ダッシュボード (優先度低下、繰越参照)

**リスク**
- Beth 第 2 週不在で RBAC スパイクの完了はオンコール中の Carmen に依存。
  ページが急増すればスパイクが滑る。緩和策: Beth が第 1 週にスパイクを
  前倒し。
- モバイルウェブ Audit Log は Alex が Saved Searches ポリッシュ中に
  仕上げる共有レイアウトプリミティブに依存。引き継ぎに注意。
```

この計画が行うこと:

- スプリント目標を冒頭に 1 文で。
- キャパシティ算数は明示的で保守的。
- 繰越は冒頭で決定（残す / 落とす / 分割）。
- P0 は実キャパシティ内に快適に収まる、ストレッチ余地あり。
- Won't-do は明示的、引き受けたくなる項目を名指す。
- リスクは緩和策付きで名指す、埋めない。

## パート 2 — メトリクスレビュー

### 良い状態とは

メトリクスレビューは数値の壁ではない。次を言う 2 ページ文書:

> 「最も重要な 3〜5 個のメトリクスはこれ。各々のトレンド、駆動していると思うもの、次に見たいもの。知っておくべきこと: <1 つの具体的事項>」。

多くのメトリクスレビューは、すべてをカバーしようとして失敗する。現在の戦略的問いにとって最重要なメトリクスを選び、動いたものを浮上、ノイズを無視。

### プロンプト

```
私とメトリクスレビューを実行します。ルール:

1. 3〜7 個のメトリクスと値 (今期、前期、あれば目標) を渡します。
   各メトリクスにつき読み上げを 1 つずつ生成してください。

2. 各メトリクスについて書く:
   - トレンド: 上昇 / 下降 / 横ばい、大きさ付き (例:「12% 上昇」)
   - 比較対象: 前期、目標、または両方
   - 仮説: 1〜2 文。何が駆動していると思うか。仮説を立てる情報が
     足りなければ、正直にそう言う。
   - フォローアップ: 次に確認したいもの (データのスライス、顧客コール、
     ローンチとの相関等)

3. 重要度順に並べる。最も動いた / 現在の戦略にとって最重要なメトリクスが先頭。

4. 末尾に、週を 3〜4 文で要約する「ヘッドライン」段落を 1 つ書く。
   これを読むエグゼクティブが知って立ち去るべきもの。

5. ノイズを埋める。メトリクスが意味的に動かず戦略的にも関連しないなら、
   末尾の「横ばい / シグナルなし」にグループ化。

声: 直接的、キャリブレートされた。ヘッジ言葉 (「かもしれない」「ありうる」)
は正直なときには OK、誤った確実性は避ける。
```

### 入力形状

```
[期間]
レポート期間: <例: 2026 年 5 月 6〜12 日週>
比較対象: <前期日付>

[戦略コンテキスト]
今四半期注意していること (例:「アクティベーション +10pp 目標」「Q2 更新サイクル」
「月中の Saved Searches ローンチ」)

[メトリクス]
各メトリクスについて:
- 名前
- 現在値
- 前期値
- 目標 (任意)
- 必要なコンテキスト (今週のローンチ、既知の異常等)
```

### 出力例

**入力:**

```
[期間]
2026 年 5 月 6 日〜12 日週
比較対象: 4 月 29 日〜5 月 5 日週

[戦略コンテキスト]
Q2 目標はアクティベーション +10pp。YTD では +6pp、Q2 終了までに +4pp 必要。
Saved Searches v1 は 5 月 30 日予定。

[メトリクス]
- WAU: 8,420 → 8,510 (+1.1%)、目標なし
- アクティベーション率: 41% → 39% (-2pp)、目標 47%
- Webhook リトライ失敗: 0.8% → 0.3% (-0.5pp)、目標 <1%
- サポートチケット件数: 142 → 168 (+18%)、目標なし
- 新規有料顧客: 12 → 14 (+2)、目標 15/週
- モバイルウェブセッションシェア: 18% → 21% (+3pp)、目標なし
- 「ビューを失った」チケット: 6 → 8 (+2)、非公式目標は 7 月までにゼロ
```

**出力:**

```
**ヘッドライン:** アクティベーションが今週 2pp 滑った、7 週間で初の低下 —
新初回フローが前スプリントで修正したエッジケースに過剰回転している可能性、
次の実験前にファネルを掘る必要あり。Webhook リトライ失敗は今や目標を
大幅に下回り安定。Saved Searches ローンチは順調、「ビューを失った」
チケットは増加 — ローンチは 18 日先と覚えておく。

---

**アクティベーション率** — 下降 2pp (41% → 39%、目標 47%)
- 比較対象: 前週と YTD トレンド (3 月 17 日週以降で初の低下)。
- 仮説: 4 月 30 日に出荷した初回フロー改訂が速度をカバレッジと交換した —
  エッジケース処理のために 2 つのオンボーディングステップを追加。アクティベーション
  までの中央値時間を遅らせて率を落とした疑い。ステップ別ファネルを見る必要。
- フォローアップ: 今週 vs 先週の新規ユーザーファネルを引く、ステップ別の
  ドロップオフを比較。金曜までにステップ 4 を巻き戻すか反復するかを判断。

**サポートチケット件数** — 上昇 18% (142 → 168)
- 比較対象: 前週。ベースライン目標なし。
- 仮説: 増加は「Saved Views」カテゴリー (6 → 8) とオンボーディング関連
  (上記アクティベーション低下と関連の疑い) に集中。品質後退ではなく、使用
  シフト。
- フォローアップ: 今週のチケットをカテゴリー別にタグ。オンボーディングが増加の
  >40% なら、アクティベーション低下と同じ根本原因。

**Webhook リトライ失敗** — 下降 0.5pp (0.8% → 0.3%、目標 <1%)
- 比較対象: 前週と目標。
- 仮説: 2 週前に出荷した冪等性 + DLQ 作業が今や完全に効果。1 週間限りの
  まぐれでなく持続的低下。
- フォローアップ: 解決とマーク。週次メトリクスから外し、今後は月次でモニター。

**新規有料顧客** — 上昇 2 (12 → 14、目標 15/週)
- 比較対象: 前週と週次目標。
- 仮説: 目標に近い、騒ぐべきものなし。
- フォローアップ: 今週はなし。Q2 累計を観察。

**モバイルウェブセッションシェア** — 上昇 3pp (18% → 21%)
- 比較対象: 前週。公式目標なし。
- 仮説: トップ 3 フローのモバイルウェブ同等性ローンチが持続的上昇を駆動。
  直近 4 週中 3 週で成長。
- フォローアップ: 来週のレビューでデバイスクラス内訳を引く、デスクトップ
  セッションのカニバリゼーションではなく増分使用であることを確認したい。

**横ばい / シグナルなし**
- WAU: +1.1%、通常の週次ばらつき内。アクションなし。
- 「ビューを失った」チケット: 6 → 8。週次分析のノイズ閾値以下、Saved
  Searches ローンチ後に再訪。
```

この読み上げが行うこと:

- 3〜4 文のヘッドラインがエグゼクティブにスクロールなしで要点を渡す。
- メトリクスは重要度順、アルファベット順ではない。
- 各メトリクスに本物の仮説、「引き続きモニター」ではない。
- フォローアップは具体的アクション、曖昧な意図ではない。
- 解決したメトリクス（Webhook リトライ失敗）は週次リストから卒業。
- ノイズは「横ばい / シグナルなし」の下に埋めて、読み上げをスキャナブルに保つ。

## スプリントとメトリクスの連動

メトリクスレビューは次のスプリント計画を駆動すべき。アクティベーションが今週 2pp 下落し、仮説が初回フローを指すなら、そのファネル調査はバックログのどこかではなく、次スプリントの P0 に属します。

ワークフロー:

1. 金曜または月曜朝にメトリクスレビューを実行。
2. 驚かせた 1〜2 個のメトリクスを特定（ポジティブまたはネガティブ）。
3. 各驚きをフォローアップに変換: データ取得、顧客コール、実験。
4. フォローアップは戦略目標に荷を背負うなら P0 項目としてスプリント計画に。

PM の仕事はループをタイトに保つこと: メトリクス → 仮説 → 実験 → メトリクス。先週のシグナルを反映しないスプリント計画はチームが漂流する方法。
