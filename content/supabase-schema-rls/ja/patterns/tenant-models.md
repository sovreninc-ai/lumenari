# テナントモデル — テナント別スキーマ vs. `tenant_id` カラム

マルチテナント Postgres には、現実的な選択肢が 2 つある。意図的に選ぶこと。

## 2 つの選択肢

### A. `tenant_id` カラム（共有スキーマ）

すべての行に `tenant_id` カラムを持たせる。RLS ポリシーがそれを使う。1 つのスキーマ、1 つのテーブル群、1 つのマイグレーション群。

**長所**
- 数千テナントへのスケーリングが安価
- 1 つのマイグレーションがすべてのテナントに反映される
- クロステナントの分析が 1 つのクエリで可能
- バックアップ、モニタリング、運用がシンプル

**短所**
- RLS のバグ = 全テナントにわたるデータ漏洩
- 単一テナントへの「データエクスポート」やハード削除が難しい
- テナントごとに異なるスキーマを持てない（カスタムフィールドは JSON か別テーブル）

### B. テナント別スキーマ

各テナントが自身の Postgres スキーマ（あるいは自身のデータベース）を持つ。マイグレーションは各テナントに適用する。

**長所**
- 強い境界 — 1 つのスキーマの RLS バグが他のスキーマに漏れない
- テナントごとのエクスポート、削除、移行が容易
- 必要ならテナントごとに異なるスキーマを持てる

**短所**
- 運用負荷がテナント数に対して線形に増加
- クロステナントのクエリは悪夢
- コネクションプールの影響（Supabase pgbouncer の設定が重要）
- マイグレーションはオーケストレーションが必要で、単一の `supabase db push` では済まない

## 判断基準

次のいずれかが当てはまる場合は、テナント別スキーマを使う:

1. 規制上、各テナントのデータが物理的に分離されている必要がある（一部の医療、一部の金融）
2. テナント数は少ないが非常に大きい（例: テナント 50 未満、各 100 万行超）
3. テナントがスキーマをカスタマイズする（カスタムフィールド、カラム）

それ以外は、**`tenant_id` カラムが正解**。Sovren Sports、Lumina Reset、TradePass がいずれもこれを使っている。

## `tenant_id` を正しく使う方法

```sql
create table public.events (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null references public.organizations(id) on delete cascade,
  -- … 他のカラム
  created_at timestamptz not null default now()
);

-- テナントカラムには必ずインデックスを張る。
create index events_organization_idx on public.events(organization_id);

-- トラフィックがテーブルに到達する前に必ず RLS を有効化。
alter table public.events enable row level security;
```

新しいテナントスコープのテーブルを追加するマイグレーションは常に: `create table` → テナントカラムへの `create index` → `enable row level security` → ポリシー。この順序。ステップ 3 を飛ばしたら、データ漏洩をデプロイしたことになる。

## テナント別スキーマを正しく使う方法

- テンプレートスキーマを 1 つ持つ。マイグレーションはテナントごとにレンダリングされる SQL テンプレート
- `public` スキーマに、テナントスラッグ → スキーマ名のレジストリテーブル
- 各セッション開始時に `search_path` をセットする接続ヘルパー
- アプリケーションコードは絶対にテナント名を SQL 文字列に連結しない（代わりにパラメタライズした `set_config` を使う）

これは余分な仕事。基準のいずれかが本当に発火しない限り、引き受けない。
