# 微文案模式

## 按钮

按钮描述结果，而非系统动作。以动词开头。

| 差 | 好 |
|---|---|
| 提交 | 发送邀请 |
| 确定 | 保存更改 |
| 处理 | 立即支付 |
| 确认 | 取消报名 |
| 是 | 删除活动 |

规则：单独读按钮文案。能看出接下来要发生什么吗？不能就重写。

破坏性操作的动词本身就是警告："删除账户" —— 不要再连按两次 "Are you sure?"。

## 空状态

空状态是用户对一个屏幕的第一印象。别浪费在 "No items found" 上。

形态：

```
[ 图标 —— 克制，不装饰 ]

一句话标题，说明有内容时这屏做什么

正文：告诉用户如何到达那里。

[ 带他们到那里的 CTA ]
```

例子：

> **你的资料库目前为空。**
> 一旦你购买了一个套件，你将下载的所有内容都会在这里。
> [ 浏览套件 → ]

> **本周没有活动。**
> 当教练安排训练或比赛时，将会显示在这里。
> [ 查看即将到来 → ]

## 错误

好的错误信息回答三个问题：
1. 发生了什么？
2. 是谁的问题（系统 or 我）？
3. 我现在该怎么办？

```
未能保存草稿。
连接断开了。请再试一次 —— 你的内容仍在这里。
[ 重试 ] [ 保存为离线副本 ]
```

要避免：
- "出错了" —— 无用
- 单独的错误码 —— 是给支持看的，不是给用户看的（放进详情，不放进标题）
- 隐性指责用户（"无效输入" —— 按谁的标准无效？）
- Stack trace

## 引导

引导的每一步只做一件事。不要把多件事塞在一起。

Apple 引导通常是：
1. **欢迎 / 价值主张屏** —— 这个 app 是做什么的，一句话
2. **唯一真正重要的许可请求** —— 仅此一个
3. **第一个真正有用的屏** —— 不是教程，是真正的产品

反模式：5 屏轮播讲每一个功能。用户还没赢得读这些的耐心。

如果某个功能需要解释，就在它第一次出现时内联解释，附 "知道了" 或 "OK" 的关闭按钮。

## 确认弹窗

留给不可逆或昂贵的操作。每一次都是摩擦税。

形态：

```
接下来要发生什么（1-2 句具体说明）

[ 取消 ] [ 动词-该操作 ]
```

例子：

> **删除这个活动？**
> 14 条 RSVP 和已上传的文件也将一并删除。
>
> [ 取消 ] [ 删除活动 ]

注意：主按钮是动作的动词，不是"是"。取消是次按钮，不等权重。

## 加载状态

三档：

1. **< 200ms** —— 不显示。眼睛察觉不到。
2. **200ms - 2s** —— 在缺失内容位置展示一个低调 spinner 或 skeleton。
3. **> 2s** —— 显式说明："正在为你生成套件推荐…" —— 让用户知道有事在为他进行。

只有在你真的无法估时时，不确定 spinner 才算诚实。能估就用进度条。

## 成功状态

成功的操作不需要一个 modal 来祝贺自己。一个 toast、一个对勾、一个轻轻滑入的"已保存"就够。

把庆祝留给真正的里程碑（首张发票收款、第 100 个客户等）—— 即便如此也要简短。
